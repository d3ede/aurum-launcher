# Aurum architecture

The native application permits one running instance using Tauri's [Single Instance plugin](https://v2.tauri.app/plugin/single-instance/), so separate windows cannot overwrite the same in-memory database. Standalone core examples are developer utilities and must run sequentially against a shared test root. Data relocation copies into a separate empty directory, retains the source, and selects the destination only after successful completion and restart.

Independent implementation. No third-party launcher code or artwork is used.

`src/`: Russian React UI, typed IPC, theme tokens, catalog, profiles, accounts, settings.
`crates/auren-core/`: platform-independent service library. Persistence, verified transfers, Minecraft metadata, loader installers, Java runtime, process supervision, OAuth, OS credential vault, catalog adapters and archive import.
`src-tauri/`: small native bridge. Dialogs return paths to Rust; the webview has no general filesystem or shell permissions.

Game data defaults to the OS application data directory. Shared assets/libraries/runtime cache are separate from UUID-named isolated instances. Metadata and profile changes are persisted atomically. Credentials are stored in the OS vault, never in profile JSON. One mutating network task at a time prevents shared-cache races. Installation publishes a completed manifest only after every required download succeeds. Cancellation preserves verified cache entries, removes partial files, and never marks a partial installation ready.

Native operations emit progress/log events. The UI never fabricates catalog entries, profiles, installation progress or launch success. Browser mode only persists appearance preferences and provides an explicitly labelled native-runtime unavailable state.

`processes.rs` restores running games at startup by discovering Java processes whose `--gameDir` resolves to an existing profile in the current data root. Command lines stay transient in native memory; tokens and command lines are never persisted. Restored sessions validate executable, directory and process start time. On Windows, stop additionally checks the precise creation FILETIME on the same process handle it terminates, preventing PID reuse from targeting a different process. Multiple existing processes for a profile are tracked together; unrelated Java applications are excluded. Closing the launcher preserves its game process. Restored status is refreshed every two seconds while games are running, and exited processes are removed instead of leaving stale status.

`modrinth_import.rs` independently reads Modrinth App's legacy `profile.json`, classic SQLite `profiles`, and current `instances`/`instance_content_sets` schemas. It follows custom data-directory settings and opens SQLite read-only without reading authentication tables. Import selections are rediscovered natively before copying; metadata supplied by the webview is never trusted. Each profile is staged and committed separately, so cancellation retains completed imports and removes the current partial copy. Game files (including arbitrary mod-specific folders, disabled mods, worlds and options) are copied independently; Modrinth logs, launcher metadata and world session locks are excluded. Only file links into Modrinth's own content store are resolved; other external links are rejected. Minecraft and Java are prepared by Aurum on first launch. Imported content is initially managed as local files; account tokens, hooks, environment variables and external Java paths are not migrated.

`microsoft_oauth.rs` implements native Authorization Code + PKCE S256 with per-attempt state and an ephemeral IPv4 loopback listener. An owned Microsoft WebView2 window performs sign-in without opening the system browser. Only Microsoft identity hosts and the current loopback callback are allowed as top-level navigation; popups and downloads are blocked. Remote content cannot invoke launcher RPC. The isolated profile preserves Microsoft cookies separately from the local UI. User closure cancels the task; validated code exchange closes the window without cancelling the subsequent Minecraft requests. Only validated callbacks belonging to the current attempt are accepted. Cancellation drops the listener and in-flight token requests; timeouts bound waiting. Client ID comes from the public build configuration, never player settings. PKCE verifiers, authorization codes and tokens remain in Rust; IPC exposes account metadata and non-sensitive phases only. Credentials remember the issuing Client ID in the OS vault for refresh and Minecraft launch arguments. See [MICROSOFT-LOGIN.md](MICROSOFT-LOGIN.md).

Public specifications used: Tauri 2 configuration and commands (https://v2.tauri.app/), Mojang version metadata (https://piston-meta.mojang.com/mc/game/version_manifest_v2.json), Fabric Meta (https://meta.fabricmc.net/), Quilt Meta (https://meta.quiltmc.org/), Forge/NeoForge Maven installer artifacts, Modrinth API (https://docs.modrinth.com/api/), CurseForge API (https://docs.curseforge.com/rest-api/), Microsoft Authorization Code with PKCE (https://learn.microsoft.com/entra/identity-platform/v2-oauth2-auth-code-flow), Eclipse Adoptium API (https://api.adoptium.net/).

## Skin library

`skins.rs` persists saved skins, local capes and per-account selections atomically in `<data>/skin-library.json`, independently of the existing profile database. Textures are normalized PNG data URIs: uploads are limited to 1 MB, skins to 64×64/64×32 and capes to 64×32, with dimensions checked before decoding. Library mutations share the engine lock; malformed libraries are reported and preserved. Existing account PNGs in `skins/` remain readable. Deleting a library item removes references without removing an account's applied texture.

The dedicated `Skins` route uses skinview3d with manual orbit controls, seven animation modes and an actual Three.js ground plane. Tile thumbnails share a queued renderer instead of allocating a WebGL context per skin. Main and editor texture loads guard against stale asynchronous image callbacks. All nine official default characters, with wide and slim arms, ship locally; provenance is recorded alongside the assets.

Microsoft appearances and owned capes are fetched using the native Minecraft account token. Remote textures must come from `textures.minecraft.net`; downloads are bounded and PNG-validated. Before changing the skin, native code checks that the selected cape belongs to the account. Microsoft skins and owned cape selections use Minecraft Services; arbitrary local capes and offline skins are launcher previews. Real authenticated remote mutations require an eligible Microsoft account and are not covered by the offline smoke test.
